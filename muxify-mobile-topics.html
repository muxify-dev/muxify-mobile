Topics stayed unavailable because Sessions only lasted as long as the Connection

Question: why did the Sessions menu say Topics were not available, until a new sign-in or an app restart?

On current master, when the Host Server gives up (no hello in 10 s, or 3 stops in 60 s), the Connection stays in Sessions only until that Connection closes. An Attach can keep one Connection open for hours, so nothing asked the Host Server again until a new sign-in or an app restart made a new Connection. The fix asks again on the same Connection when the cause can pass. This happens on a return from the background, and on a screen's use one minute or more later. A regression test shows the fault on the old code and the fix on the new code.

Did the work do what was asked? Yes, with one difference: the report says "unsupported", but the app shows "Topics are unavailable on <Host>: <reason>". I found no path that shows "unsupported" in the Sessions menu (see the message). I did not reproduce the fault on a real device. The cause is from reading the code and from the test.

1 · On master, a Host Server that gave up stays down for the life of the Connection, and an Attach keeps the Connection alive

A worked case, with the numbers from the code: the terminal is open on a Host. iOS suspends the app for more than 45 s. During that time the Host Server exits, because nothing reaches it (ADR 0025: "the server exits after 45 s of silence"). When the app returns, the link is slow.

  • Two causes give up with no user action: no-hello → unavailable.noAnswer(), and 3 stops in STOP_WINDOW_MS (60 s) → stoppedRepeatedly. A restart has no wait, so failures that come fast use the 3 stops in milliseconds. (src/ssh/host-server.ts:257, :273; before the fix: :248, :264)
  • On a return, an entry with an Attach only refreshed its Listing feed. Only a Connection with no Attach and no live server was dropped. (master src/ssh/host-connections.ts:646-648)
  • ADR 0028 keeps a slow link that still answers tmux, and ADR 0031 keeps a Connection over a return. ADR 0025's rule "the next Connection tries again" assumed that a new Connection came soon. These two later ADRs removed that assumption.
  • The Title Sheet's Try again (rereadTopic, readHost) uses the same Host Server object, which stays in Sessions only, so it shows the same note. (src/hooks/use-title-sheet.ts:304-323, src/ssh/topic-feed.ts:51-53)

2 · The words on the screen are "unavailable", and the app shows "unsupported" in no Sessions menu

The note comes from one function: topicsUnavailable(host, reason) → "Topics are unavailable on ${host}: ${reason}" (src/topics/host-topics.ts:50-51). It reaches the Title Sheet through the live Listing: live.server.kind === 'sessions-only' → { kind: 'unavailable' } (src/topics/host-topics.ts:200-202). "unsupported" is only a HostServerError code (src/ssh/host-server-channel.ts:53), the phone sends it as a reply (:526), and a server can send it back for a request it does not know (:309). Only such an error's message can reach a screen (topic-feed.ts:58), never the code word. So I take "unsupported" in the report to mean this note. The reason text that the user saw is not known. Possible reasons are "the Host Server did not answer" or "stopped 3 times in a minute". A reason "too old" would not clear with a sign-in on the same Host, so that reason does not match the report.

4 · The fix asks the Host Server again on the same Connection, only when the cause can pass

Before (master)

  • Sessions only, any cause → stays until the Connection closes.
  • Return with an Attach → Listing refresh only.
  • Screen read → tmux read. The server state does not change.

After

  • Sessions only marks if its cause can pass (canPass): no answer, or 3 stops.
  • Return with an Attach → tryAgain(), then the Listing refresh.
  • Any screen use (read, write, hold, onServer) → tryAgain(60 s): only when Sessions only began 60 s or more before.
  • A retry resets the 3-stop budget. "Too old" and "not installed" never retry here: the Host CLI install already starts the server again when it answers installed or updated (host-server.ts:318-337).

Why 60 s on the use path: the Host Screen's Sessions-only list reads the Host each time the state becomes Sessions only (use-host-listing.ts:93-118). With no wait, that read would start the server, the server would fail, and the read would start it again, in a loop. When the server becomes live, the Listing feed and the Topic feed subscribe again by themselves (host-listing-feed.ts:123-125, topic-feed.ts:63-65).

The diff shows the two source files. Also changed: five test fakes get tryAgain: () => {}, there is a new ADR 0033, and CONTEXT.md → Host Server.

Not done, and what is not known

  • No device check. I did not see the fault on a phone. I did not run the e2e suites. A device test: open the Terminal, keep the app in the background for more than 45 s on a slow link, then return.
  • The reason text is not known. The report does not say which reason it showed. If the log has "Sessions only: …" lines from connections: <Host>: Host Server:, they tell which cause it was.
  • The timer during a suspension is a guess. If a restart begins just before iOS suspends the app, the 10 s hello timer can fire on resume before the buffered hello is read. That would give a false "did not answer". I did not confirm the order of events on iOS. The fix recovers from it in both cases.
  • No backoff between fast restarts. Three fast failures still use the budget in milliseconds. The fix recovers later, but it does not make the first give-up less likely. This is a possible follow-up.
  • Up to 60 s still stuck when no return comes. For example, the user opens the menu 20 s after the give-up. A refresh button for the Host Server in the menu would close this gap. Not built.
